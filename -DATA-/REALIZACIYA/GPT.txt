Да. Для такой задачи **Lightweight Charts подходит очень хорошо**, но я бы строил систему не как «страница → Polymarket API → график», а как маленький realtime-terminal:

**Polymarket WebSocket → collector → нормализация rolling-рынков → локальная БД/Parquet → WebSocket вашего приложения → Lightweight Charts.**

Причина принципиальная: официальный `/prices-history` сейчас не является источником секундной истории. У него предусмотрены агрегированные интервалы вплоть до `1m`, и `fidelity` тоже задаётся в минутах. Секундные/субсекундные данные нужно получать из realtime-потока и **самостоятельно сохранять**. ([Polymarket Documentation][1])

Ниже я бы проектировал именно так.

# 2. Самое важное: что именно считать «ценой»

Это надо решить **до написания программы**.

У Polymarket есть минимум три разных величины:

### A. Last Trade

Цена последней сделки.

Realtime WebSocket сообщает событие:

```json
{
  "event_type": "last_trade_price",
  "asset_id": "...",
  "price": "0.63",
  "size": "219.21",
  "side": "SELL",
  "timestamp": "..."
}
```

Это реальная цена исполнения сделки. ([Polymarket Documentation][2])

### B. Best Bid

Лучшая цена, по которой кто-то сейчас готов купить.

### C. Best Ask

Лучшая цена, по которой кто-то сейчас готов продать.

### D. Midpoint

```text
(best_bid + best_ask) / 2
```

Polymarket прямо указывает, что midpoint является отображаемой вероятностью рынка; однако при широком spread Polymarket может показывать вместо midpoint last trade price. ([Polymarket Documentation][3])

## Я рекомендую

Для твоего основного графика сделать:

**по умолчанию → Midpoint**

и дополнительно хранить:

```text
mid
bid
ask
last_trade
spread
```

Потому что тогда ты сможешь потом переключиться:

```text
[ MID ] [ LAST ] [ BID ] [ ASK ]
```

А если ты занимаешься анализом поведения рынка, это намного ценнее одной линии.

# 3. Очень важная поправка к «рынок всегда стартует с 50¢»

Я бы **не кодировал правило `new market = price 0.50`**.

Это визуально может наблюдаться очень часто, но технически нельзя строить систему с таким предположением.

В документации Polymarket прямо указано, что у нового рынка нет гарантированной начальной цены: цена появляется из выставленных заявок/первых сделок. ([Polymarket Documentation][3])

То есть приложение должно делать:

```text
market created
     ↓
book snapshot
     ↓
bid / ask
     ↓
midpoint
     ↓
first observed price
```

А не:

```text
market created
     ↓
price = 0.50
```

Можно визуально показывать 50¢ как reference line, но **не подставлять 50 как историческую рыночную точку**.

# 5. Для твоих BTC-рынков вообще не нужно искать рынок перебором

Это один из самых приятных моментов.

У rolling crypto markets slug имеет детерминированную структуру:

```text
btc-updown-5m-UNIX_TIMESTAMP
```

и

```text
btc-updown-15m-UNIX_TIMESTAMP
```

Для 5 минут:

```text
+300 секунд
```

Для 15 минут:

```text
+900 секунд
```

Это также подтверждается актуальным обсуждением `py-clob-client`, где показан такой способ получения следующего 15m/5m market slug. ([GitHub][5])

Поэтому приложение может заранее вычислять:

```ts
const currentWindow =
    Math.floor(Date.now() / 300_000) * 300_000;

const slug =
    `btc-updown-5m-${currentWindow / 1000}`;
```

Следующий:

```ts
const nextSlug =
    `btc-updown-5m-${currentWindow / 1000 + 300}`;
```

Для 15m:

```ts
const currentWindow =
    Math.floor(Date.now() / 900_000) * 900_000;
```

# 6. Но я бы всё равно не полагался только на вычисление slug

Лучший вариант:

```text
                    ┌───────────────┐
                    │ deterministic │
                    │ next slug     │
                    └───────┬───────┘
                            │
                            ▼
                       Gamma API
                            │
                            ▼
                   получаем market
                   + token IDs
                            │
                            ▼
                       WebSocket
```

А параллельно слушаем события Polymarket:

```text
new_market
market_resolved
```

При `custom_feature_enabled=true` Market WebSocket может отдавать lifecycle-события `new_market` и `market_resolved`, а также `best_bid_ask`. ([Polymarket Documentation][2])

Но для переключения rolling рынка я бы использовал **детерминированный timestamp как primary mechanism**, а `new_market` как дополнительную страховку.

Причина: уже встречались случаи, когда пользователи наблюдали задержку между фактическим началом crypto-window и событием обнаружения нового рынка.

Полный realtime feed может дать:

Я бы использовал **не один event**, а несколько.

## `book`

Пригодится для восстановления состояния книги.

Сообщение содержит:

```text

```

([Polymarket Documentation][2])

## `price_change`

Это очень важный поток.

Он сообщает изменение уровня книги:

```json
{
  "price": "0.63",
  "size": "200",
  "side": "BUY",
  "best_bid": "0.63",
```

Именно на основании этих событий надо обновлять состояние order book.

Это фактические исполнения:

```text

size

```

([Polymarket Documentation][2])

Это отдельный источник, который надо сохранять независимо.

# 9. Как я бы определял значение для главной линии

При каждом поступившем событии:

### Если есть новое best bid/ask

```text
mid = (bid + ask) / 2
```

### Если spread слишком широкий

Можно отдельно хранить:

```text
displayed_price
```

по логике Polymarket:

```text
if ask - bid <= 0.10:
    displayed = midpoint
else:
    displayed = last_trade
```

Так будет максимально близко к тому, что видит пользователь на Polymarket. ([Polymarket Documentation][3])

Но для аналитики я бы всё равно **не выбрасывал midpoint и last отдельно**.

# 13. Шкала справа

Нужно отключить автоматическую шкалу и зафиксировать:

```text
0
10
20
30
...
90
100
```

Например концептуально:

```ts
priceScaleId: 'right'

rightPriceScale: {
    visible: true,
    autoScale: false,
}
```

и диапазон:

```text
0 → 100
```

У последних версий Lightweight Charts есть API `setVisibleRange()` у price scale, так что это можно сделать программно. ([tradingview.github.io][11])

Это **очень желательно** для твоего приложения.

Иначе график 46¢–57¢ будет автоматически растянут и движение визуально станет огромным, хотя рынок практически не изменился.

# 14. Источник времени

Очень важно.

**Не использовать время браузера как время события.**

У Polymarket WebSocket есть timestamp самого market event:

```text
timestamp: "1757908892351"
```

то есть миллисекунды Unix time. ([Polymarket Documentation][7])

В хранилище надо сохранять:

```text
event_ts
received_ts
```

Например:

```text
event_ts    = 1782753357.235
received_ts = 1782753357.254
```

Разница:

```text
19 ms
```

А это потом даст тебе возможность оценить latency.

---

# 15. Почему нужно хранить `received_ts`

Это очень полезно именно для твоей задачи.

Например:

```text
Polymarket event timestamp:
12:00:01.230

твой сервер получил:
12:00:01.251

browser получил:
12:00:01.265
```

Ты тогда можешь построить:

```text
market latency
collector latency
browser latency
render latency
```

и понять, действительно ли приложение работает realtime.

---

# 16. Самая важная архитектурная ошибка, которую надо избежать

Не делай:

```text
WebSocket
  ↓
React state
  ↓
setData(...)
  ↓
chart
```

для каждого сообщения.

Это очень быстро превратит приложение в тормозную конструкцию.

Lightweight Charts сама рекомендует для realtime использовать:

```ts
series.update(...)
```

а не постоянно:

```ts
series.setData(...)
```

потому что `setData()` заменяет весь массив данных. ([GitHub][12])

# 18. Почему нужен backend

Можно технически подключить браузер напрямую:

```text
Browser → Polymarket WebSocket
```

Это действительно возможно для публичного market stream.

Но полноценное приложение я бы всё равно сделал с backend.

Потому что тебе нужна **история**.

Realtime WebSocket не является историческим хранилищем.

Если приложение запустилось сегодня:

```text
12:00
```

оно не может спросить websocket:

```text
дай все события вчера между 12:00 и 13:00
```

# 19. У Polymarket нет подходящего официального секундного history API

Это критическая часть всей системы.

Официальный:

```text
GET /prices-history
```

поддерживает:

```text
1m
1h
6h
1d
1w
max
```

и `fidelity` задаётся в минутах. ([Polymarket Documentation][1])

То есть:

```text
секунды ← НЕ получить
```

из обычного history endpoint.

Поэтому надо писать собственный collector.

# 20. Collector должен работать постоянно

Например:

```text
collector
   │
   ├── BTC 5m current
   ├── BTC 5m next
   ├── BTC 15m current
   └── BTC 15m next
```

И постоянно сохранять данные.

Тогда через месяц у тебя появляется:

```text
30 дней × 288 × 5m markets
```

для 5m:

```text
≈ 8 640 markets
```

и

```text
30 дней × 96 × 15m markets
```

для 15m:

```text
≈ 2 880 markets
```

---

# 21. Я бы подписывался заранее на CURRENT и NEXT market

Например сейчас:

```text
current = btc-updown-5m-...
next    = btc-updown-5m-...
```

Подписываем:

```text
current YES
current NO
next YES
next NO
```

Когда подходит boundary:

```text
current → historical
next    → current
next+1  → new next
```

То есть подписка постоянно поддерживается с запасом.

Это уменьшает риск потери самого начала нового market.

---

# 22. Почему подписывать и YES, и NO

Можно получать только YES.

Но я бы сохранял оба.

Потому что в бинарном рынке примерно:

```text
YES + NO ≈ 1
```

Но реальные данные помогут диагностировать:

```text
spread
liquidity
imbalance
book state
```

Кроме того, при проблемах одного token stream второй является полезной проверкой.

Storage:

```text
market
 ├── yes_token
 └── no_token
```

# 29. Очень важная проблема отсутствующих секунд

Допустим:

```text
12:00:00  50
12:00:01  50.2
12:00:02  нет данных
12:00:03  нет данных
12:00:04  51
```

Не надо автоматически считать:

```text
50.2
50.2
50.2
51
```

как реальные цены.

Надо хранить:

```text
observed_at
```

и отдельно различать:

```text
no event
```

от

```text
price unchanged
```

# 30. Но для визуальной линии можно сделать carry-forward

Например:

```text
raw:

12:00:00 50
12:00:01 50.2
12:00:04 51
```

визуальная 1s серия:

```text
12:00:00 50.0
12:00:01 50.2
12:00:02 50.2
12:00:03 50.2
12:00:04 51.0
```

Но в данных должно оставаться:

```text
observed=false
```

у 02 и 03.

Это позволит потом делать правильный backtest.

# 31. Главная проблема rolling markets

Допустим:

```text
17:00:00 → market A
17:05:00 → market B
```

A:

```text
50 → 73
```

B:

```text
50 → 20
```

Нельзя соединять:

```text
73 ─────────── 50
```

потому что возникает ложный скачок.

Lightweight Charts специально поддерживает **WhitespaceData**, которое позволяет сделать разрыв между участками серии. ([tradingview.github.io][13])

Поэтому:

```text
market A:
50 → 55 → 60 → 73

whitespace

market B:
50 → 47 → 38 → 20
```

```text
Market ends:   18:30:00
```

Это будет очень удобно визуально.

# 33. Необходимо различать время рынка и абсолютное время

Каждая запись должна иметь:

```text
market_start
market_end
event_ts
```

Например:

```text
market_start = 18:25:00
event        = 18:27:43.211
market_end   = 18:30:00
```

Тогда можно легко показать:

```text
time remaining = 2m 16.789s
```

и:

```text
elapsed = 163.211s
```

---

# 34. Что делать в момент rollover

Допустим:

```text
17:04:59.999
```

старый рынок.

И:

```text
17:05:00.000
```

новый.

Нужно сделать атомарно:

```text
OLD MARKET
   ↓
stop active
   ↓
save last state
   ↓
insert market boundary
   ↓
NEW MARKET
   ↓
subscribe
```

Не делать:

```text
price from old market
+
price from new market
```

одним непрерывным рынком.

---

# 35. Самая безопасная схема rollover

Заранее держать:

```text
ACTIVE
NEXT
```

Например:

```text
current token:
btc-updown-5m-178...
 
next token:
btc-updown-5m-178...+300
```

Когда наступает:

```text
next.startDate <= now
```

делаем:

```text
current = next
next = generateNextSlug()
fetch metadata
subscribe next
```

# 36. Gamma API здесь используется только для discovery

То есть:

# 39. Обязательно нужен reconnect

WebSocket может:

```text

timeout
close
stall
```

Поэтому:

```text
connection
   ↓
heartbeat
   ↓
timeout
   ↓
reconnect
   ↓
resubscribe
   ↓
book snapshot
```

Нельзя считать:

```text
socket connected = data guaranteed
```

# 40. После reconnect нельзя просто продолжить

Очень частая ошибка.

Предположим:

```text
12:00:00.000 disconnect
12:00:00.800 reconnect
```

Возможно, между ними были события.

Поэтому после reconnect я бы делал:

```text
new book snapshot
+
current midpoint/bid/ask
```

и отмечал:

```text
data_gap = true
```

если пропуск действительно произошёл.

# 41. Book hash нужно использовать

В order book есть:

```text
hash
```

Polymarket прямо документирует его как идентификатор состояния книги, который можно использовать для обнаружения изменения. ([Polymarket Documentation][15])

Это очень полезно для диагностики.

Например:

```text
last_hash != current_hash
```

значит состояние книги изменилось.

# 42. Tick size нельзя хардкодить

Сегодня можно увидеть:

```text
0.01
```

Но WebSocket предусматривает событие:

```text
tick_size_change
```

и документация приводит пример:

```text
oldTickSize: 0.01
newTickSize: 0.001
```

([Polymarket Documentation][2])

То есть приложение должно брать:

```text
tickSize
```

из market/book metadata.

# 43. Поэтому price formatter должен быть динамический

Например:

```text

63.00¢
```

а если:

```text

```

```text
63.700¢
```

Не надо писать:

```ts
value.toFixed(2)
```

навсегда.

# 44. WebSocket-события надо дедуплицировать

У каждого события могут быть:


И у тебя должен существовать event ID:

# 45. Нужна проверка последовательности

например:


# 51. Почему это будет быстро

Lightweight Charts использует HTML5 canvas и изначально ориентирован на производительность. ([GitHub][16])

Realtime обновление через:

```ts
series.update(...)
```

не заставляет библиотеку каждый раз пересобирать весь массив. ([GitHub][12])

А в версии 5.1+ есть data conflation для больших наборов данных; для твоего приложения это особенно интересно, когда пользователь отдаляется от графика и десятки тысяч точек уже физически невозможно показать по одной. ([GitHub][8])

# 70. Особенность времени Lightweight Charts

В data series время будет Unix seconds:

```ts
time: 178...
```

Но событие Polymarket может приходить в milliseconds:

```text
1782753357257
```

поэтому:

```ts
const chartTime = Math.floor(timestampMs / 1000);
```

Но!

Тут возникает проблема: тебе нужна **минимум секундная детализация**.

Несколько событий:

```text
12:00:01.100
12:00:01.200
12:00:01.900
```

при переводе:

```text
12:00:01
```

становятся одним timestamp.

И это нормально, **если график именно 1s** и ты заранее агрегируешь события до секунды.

# 73. Какой именно market URL использовать

Ты привёл:

# 131. Что особенно важно именно с учётом актуального состояния Polymarket

На август 2026 я бы учитывал следующие вещи:

**1. Не использовать `/prices-history` как источник секундной истории.**
Он остаётся агрегированным историческим API. ([Polymarket Documentation][1])

**2. Основной realtime источник — Market WebSocket.**
Он отдаёт `book`, `price_change`, `last_trade_price`, `tick_size_change` и дополнительные lifecycle/top-of-book события. ([Polymarket Documentation][7])

**3. Не хардкодить tick size.**
Есть realtime `tick_size_change`. ([Polymarket Documentation][2])

**4. Не хардкодить стартовую цену 50¢.**
Polymarket прямо описывает, что начальная цена возникает из рынка. ([Polymarket Documentation][3])

**5. Не полагаться на `new_market` как единственный механизм rollover.**
Для rolling markets timestamp slug позволяет заранее вычислять следующий рынок; события lifecycle следует использовать как дополнительную страховку. ([GitHub][5])

**6. Хранить metadata и realtime отдельно.**

**7. Не смешивать рынки при построении линии.**

**8. Использовать `series.update()` для realtime в Lightweight Charts.** ([tradingview.github.io][18])

**9. Использовать whitespace / market boundaries между rolling markets.** ([tradingview.github.io][13])

**10. Версию Lightweight Charts зафиксировать на 5.2.x, а не зависеть от плавающего master.** Последний стабильный релиз сейчас — 5.2.0. ([GitHub][8])

```text

    React + TypeScript + Vite
    Lightweight Charts 5.2

    Node.js + TypeScript

    Polymarket CLOB WebSocket

    Gamma API

    Parquet

    last trade

    1s / 5s / 15s / 30s / 1m

    BTC 5m
    BTC 15m

Rolling
    deterministic timestamp slug
    + lifecycle events as fallback

Chart range
    0–100¢ fixed

Data
    raw event level
    aggregated chart level
```

### Самая важная мысль

**Сам график — самая простая часть.** Lightweight Charts с этим справится без проблем. Сложность находится в **правильном сборе и реконструкции истории rolling-рынков**.

Я бы поэтому сначала написал **надёжный collector**, который 24/7 собирает `BTC 5m + BTC 15m` из Polymarket WebSocket и сохраняет raw event data. Затем поверх него уже сделать красивый Lightweight Charts frontend. Так ты не окажешься в ситуации, когда через неделю выясняется, что график красивый, но секунды за предыдущие дни нигде не сохранились.
