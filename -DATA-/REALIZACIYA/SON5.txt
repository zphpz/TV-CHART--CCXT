Разберусь с актуальным состоянием API Polymarket и lightweight-charts, прежде чем писать план — тут важна свежая информация, потому что оба продукта активно меняются.Проверил актуальную документацию Polymarket (за последний месяц там многое изменилось, включая критичное изменение 7 августа) и текущий API lightweight-charts v5. Ниже — развёрнутый план с учётом реального состояния на сегодня, 13 августа 2026.

Кстати: обе ваши ссылки указывают на **один и тот же** 5-минутный рынок (`btc-updown-5m-1786491900`) — вторая, судя по всему, должна была вести на 15-минутный (`btc-updown-15m-...`), просто вставился не тот URL. Ниже расписано, как оба случая обрабатывать одинаково.

## 1. Архитектура целиком

```
Polymarket CLOB WebSocket (книга заявок/сделки)  ─┐
Polymarket RTDS WebSocket (спот- и TWAP-цена BTC) ─┼─► [опц. тонкий relay-сервер] ─► браузер
Polymarket Gamma API (метаданные рынка, poll)     ─┘         │
                                                        буфер тиков (1с)
                                                               │
                                                     ресемплинг под текущий ТФ
                                                               │
                                                      lightweight-charts (LineSeries)
```

Два варианта, как тянуть данные:

- **Напрямую из браузера** — самый простой старт. WebSocket не подчиняется CORS так, как fetch/XHR (preflight для него не делается, браузер просто открывает соединение), и в документации Polymarket нет упоминаний о блокировке по Origin для публичного market-канала. Несколько сторонних no-code/JS-инструментов уже стримят этот канал прямо из клиентского кода.
- **Через свой тонкий backend-relay** (Node/Bun, один WS вверх к Polymarket → раздача вниз всем вкладкам/клиентам) — надёжнее, но добавляет сервис.

**Рекомендация**: начинайте с прямого подключения, чтобы быстро проверить всю цепочку. Переходите на relay, если: (а) будет больше одной вкладки/пользователя одновременно — незачем плодить N подключений к Polymarket, (б) хотите пережить сворачивание вкладки в фоне (мобильные браузеры троттлят таймеры и WS в неактивных вкладках — это ломает точность 5-минутного rollover), (в) хотите копить свою историю тиков на сервере (ниже объясню, почему история от самого Polymarket для этого не подходит).

## 2. Источники данных Polymarket

### 2.1 Как найти нужный рынок (Gamma API)

База: `https://gamma-api.polymarket.com`, авторизация не нужна.

```
GET https://gamma-api.polymarket.com/events/slug/btc-updown-5m-1786491900
```

Ответ содержит событие (event) со списком markets, каждый market содержит id, slug, question, conditionId и clobTokenIds.

**Важная ловушка**: outcomePrices, outcomes и clobTokenIds приходят как JSON-строки, а не готовые массивы — их нужно явно JSON.parse(), иначе market.outcomePrices[0] даст вам символ "[" вместо цены.

```js
const res = await fetch(`https://gamma-api.polymarket.com/events/slug/${slug}`);
const event = await res.json();
const market = event.markets[0];
const tokenIds = JSON.parse(market.clobTokenIds); // ["UP_id", "DOWN_id"]
const outcomes = JSON.parse(market.outcomes);      // ["Up", "Down"]
```

Обязательно сверяйте `outcomes[i]` с `tokenIds[i]` по индексу — перепутать Up/Down token id — классическая ошибка, из-за которой весь график получается инвертированным.

**Как вычислить slug следующего окна заранее.** Судя по документации и по коду стороннего торгового бота, 5-минутные BTC-рынки Polymarket следуют фиксированным таймстемпам, кратным 300 (unix epoch); бот не ищет рынок, а вычисляет активный по часам: window_ts = now − (now % 300), slug = "btc-updown-5m-{window_ts}" — то есть таймстемп в slug это **начало** окна. Я перепроверил это вручную по нескольким вашим и найденным примерам ссылок — сходится. Для 15-минутного рынка по аналогии ожидается то же самое, но с шагом 900 и префиксом `btc-updown-15m-` — это уже не подтверждено настолько же явно, стоит проверить эмпирически перед тем как полагаться на это в проде.

Это официально нигде не задокументировано как гарантированный контракт, поэтому в проде используйте это как быстрый путь, но всегда подтверждайте существование рынка реальным запросом к Gamma, и логируйте, если вычисленный slug вдруг вернул 404 — это будет сигналом, что схема поменялась.

### 2.2 Реальное время — CLOB WebSocket, market-канал

| Канал | URL | Heartbeat | Зачем |
|---|---|---|---|
| CLOB market | `wss://ws-subscriptions-clob.polymarket.com/ws/market` | текстовый `PING` раз в 10с → сервер отвечает `PONG` | книга заявок, цена, сделки, жизненный цикл рынка |
| RTDS | `wss://ws-live-data.polymarket.com` | текстовый `PING` раз в 5с | спот- и (с 7 авг) TWAP-цена самого BTC |

Подписка отправляется сразу после открытия соединения: {"assets_ids": ["<token_id>"], "type": "market"}. Базовые события: book (полный снепшот стакана), price_change (изменение уровня в стакане), last_trade_price (цена последней сделки), tick_size_change (изменение минимального шага цены). Если добавить custom_feature_enabled: true, дополнительно приходят best_bid_ask (лучшие бид/аск и спред), new_market и market_resolved (события жизненного цикла рынка). Токены можно добавлять/убирать на лету без пересоздания соединения: {"assets_ids": [...], "operation": "subscribe"/"unsubscribe"} — это то, что вам нужно для rollover каждые 5/15 минут.

**Что считать "ценой" для линии графика.** Есть два кандидата: midpoint (bid+ask)/2 и last_trade_price. Сам Polymarket в своём UI использует такое правило: если спред между bid и ask больше $0.10, интерфейс показывает цену последней сделки вместо midpoint. Разумно повторить эту же логику — тогда график будет вести себя так же, как то, что видят пользователи на сайте, и не "залипнет" на устаревшем midpoint в моменты тонкой ликвидности.

```js
function effectivePrice({ bestBid, bestAsk, lastTradePrice }) {
  const spread = bestAsk - bestBid;
  const mid = (bestBid + bestAsk) / 2;
  return spread > 0.10 && lastTradePrice != null ? lastTradePrice : mid;
}
```

### 2.3 Вспомогательные REST-эндпоинты — и их реальные ограничения

`GET https://clob.polymarket.com/prices-history?market=<token_id>&interval=...&fidelity=<минуты>` — fidelity задаётся в минутах, а interval принимает max/all/1m/1w/1d/6h/1h. Для 1-секундной точности это **не подходит** — минимальная гранулярность там уровня минут. Хуже того: известная проблема — для уже закрытых/резолвнутых рынков эндпоинт отдаёт пустые данные на гранулярности мельче 12 часов, даже если по факту цена активно двигалась. Вывод: не пытайтесь восстановить секундную историю уже прошедшего 5-минутного окна через этот эндпоинт — используйте его только как грубый fallback для бэкофилла на старте (если приложение открылось посреди уже идущего окна), а полноценную секундную "историю" ваше приложение должно писать само, по мере получения тиков из WebSocket.

`GET /book`, `/price`, `/midpoint` — снепшоты на текущий момент, полезны сразу после подписки, чтобы отрисовать первую точку графика мгновенно, не дожидаясь следующего тика по WS.

### 2.4 RTDS — если захотите оверлей реальной цены BTC

Отдельно от вероятностной цены рынка, можно подтянуть саму цену BTC для сравнения ("Price to Beat" — так это называется в интерфейсе самого Polymarket: каждая страница рынка показывает live "Price to Beat" — опорную цену BTC на начало окна, и текущую живую цену BTC). Это отдельный канал, `wss://ws-live-data.polymarket.com`, топики `crypto_prices` (Binance) / `crypto_prices_chainlink` (спот) — но см. следующий раздел, **это уже устаревший для целей резолюции способ**.

## 3. ⚠️ Главное недавнее изменение: переход на Chainlink TWAP-резолюцию (7 августа 2026)

Это прямо отвечает на вашу просьбу про "последние изменения" — и изменение случилось буквально на этой неделе.

До 7 августа рынки "up/down" резолвились по **мгновенному снепшоту** цены в момент закрытия окна. Это оказалось уязвимо: исследование Stanford и SMU по 5-минутному BTC-контракту Polymarket выявило манипуляционный паттерн — 821 кошелёк заработал порядка $8.2 млн на манипулируемых циклах, а розничная ликвидность несла основные потери. В ответ Polymarket объявил переход: с 2026-08-07T00:00:00Z резолюция крипто-рынков up/down происходит через Chainlink TWAP вместо мгновенного снепшота — 30-секундный TWAP для 5-минутных рынков и 60-секундный TWAP для 15-минутных и 4-часовых.

Что это значит для вашего приложения:

- **Механика живой цены (то, что вы рисуете на графике) не изменилась** — book/price_change/last_trade_price работают по-прежнему, ваш основной план из раздела 2.2 остаётся рабочим без изменений.
- **Изменилось то, что определяет исход Up/Down.** И "Price to Beat" на старте окна, и финальная цена на закрытии теперь — не мгновенное число, а среднее по 30/60-секундному окну. Если вы захотите когда-нибудь показать "к чему сейчас идёт резолюция" — сравнивать нужно TWAP с TWAP, а не спот с спотом: обычный `crypto_prices_chainlink` (спот) больше не отражает то, что реально решает исход.
- Актуальный поток именно для TWAP: через RTDS без учётных данных — топики crypto_prices_twap_thirty (30с) и crypto_prices_twap_sixty (60с), либо через типизированный SDK — топик prices.crypto.chainlink.twap с параметром windowSeconds: 30 | 60. Есть и прямой доступ через Chainlink Data Streams — но он требует учётных данных, платный (от $150/мес за фид) и документация прямо предупреждает запускать это только на доверенном бэкенде, никогда не встраивая credentials в браузер/мобильное приложение — для вашей задачи (просто рисовать линию) это не нужно, RTDS-релей бесплатен и без ключей.
- Практическое следствие для восприятия графика: в последние ~30–60 секунд каждого окна цена уже не "щёлкает" в 0 или 100 по одному тику, а сходится плавнее, поскольку резолюция усредняет — не пытайтесь это "чинить", это ожидаемое поведение новой механики.

Отдельно, менее релевантно для чтения данных, но стоит знать: в апреле 2026 Polymarket полностью мигрировал CLOB на V2-контракты — новый Exchange-контракт, новая структура ордера, залог сменился с USDC.e на pUSD, старые V1 SDK и V1-подписанные ордера перестали работать. Это касается **размещения ордеров**, а не публичного чтения рынка/WebSocket — на ваш график это не влияет, но если проект когда-нибудь вырастет до реальной торговли по этим же данным, знайте, что весь V1-код и туториалы в интернете сейчас неактуальны.

## 4. Rollover — переключение рынка каждые 5/15 минут (сердце приложения)

1. Вычисляете границу текущего и следующего окна по часам (`now − now%300`, `+300`).
2. За ~10–15 секунд до границы запускаете попытки получить slug/токены **следующего** окна через Gamma (с ретраями раз в секунду — рынок может публиковаться не мгновенно). Кэшируете результат.
3. Ровно в момент границы — на **уже открытом** WS-соединении отправляете `unsubscribe` от старых token_id и `subscribe` на новые (см. 2.2 — переподключение не требуется).
4. Параллельно слушаете `market_resolved` (с `custom_feature_enabled: true`) на текущем токене как подтверждающий сигнал, что старое окно завершилось — можно покрасить последнюю точку в зелёный/красный по факту исхода. Важная оговорка: из документации не до конца ясно, глобальный ли это поток (все рынки платформы разом) или он ограничен вашей подпиской — на всякий случай фильтруйте по полю `market`/`asset_id` в payload, а не полагайтесь только на факт получения события.
5. Визуально никакого специального "сброса на 50" делать не нужно — если вы рисуете линию по реальному unix-времени (а не по "секундам с начала сессии"), новая цена ~50 сама ляжет следующей точкой сразу после последней точки закрывшегося рынка (~0 или ~100), и график естественно превратится в "пилу" — это и есть корректное отображение реальности rolling-рынка.

```js
async function scheduleRollover(windowSec, prefix) {
  const start = Math.floor(Date.now() / 1000 / windowSec) * windowSec;
  const nextStart = start + windowSec;
  const msUntilNext = nextStart * 1000 - Date.now();

  setTimeout(async () => {
    let next = null;
    for (let i = 0; i < 10 && !next; i++) {
      next = await fetchMarket(`${prefix}-${nextStart}`);
      if (!next) await new Promise(r => setTimeout(r, 1000));
    }
    preloadedNext = next; // может быть null, если рынок так и не появился — обработайте это
  }, Math.max(msUntilNext - 15000, 0));

  setTimeout(() => {
    ws.send(JSON.stringify({ assets_ids: activeTokenIds, operation: 'unsubscribe' }));
    if (preloadedNext) activeTokenIds = preloadedNext.tokenIds;
    ws.send(JSON.stringify({ assets_ids: activeTokenIds, operation: 'subscribe' }));
    scheduleRollover(windowSec, prefix);
  }, msUntilNext);
}
```

Если пойдёте по пути backend-relay — эту логику лучше держать именно на сервере: точность `setTimeout` в фоновой вкладке браузера (особенно мобильной) не гарантирована, а на сервере таймер не троттлится.

## 5. График: lightweight-charts v5

### 5.1 Версия — важно

Библиотека сейчас на 5.2.0, и между v4 и v5 поменялся способ создания серии: вместо chart.addLineSeries({...}) теперь chart.addSeries(LineSeries, {...}), с явным импортом LineSeries из пакета. Очень много туториалов и ответов на Stack Overflow в интернете написаны под v4 и просто не заработают ("addLineSeries is not a function") — ориентируйтесь на официальный сайт `tradingview.github.io/lightweight-charts/docs/next`, а не на первый попавшийся гайд.

### 5.2 Инициализация под ваши требования (ось 0–100, время снизу с секундами)

```js
import { createChart, LineSeries } from 'lightweight-charts';

const chart = createChart(container, {
  timeScale: {
    timeVisible: true,     // без этого не увидите время вообще
    secondsVisible: true,  // без этого — только часы:минуты, без секунд
  },
  rightPriceScale: { autoScale: false }, // фиксируем 0-100, а не авто-подгонку
});

const line = chart.addSeries(LineSeries, {
  priceFormat: { type: 'price', precision: 1, minMove: 0.1 }, // шаг 0.1¢ по умолчанию
  autoscaleInfoProvider: () => ({ priceRange: { minValue: 0, maxValue: 100 } }),
});
```

Отдавайте в серию значения уже умноженными на 100 (т.е. в "центах" 0–100), тогда ось сразу читается так, как вы просили, без кастомных форматтеров.

Реальный tick size рынка не всегда 1 цент — событие tick_size_change явно сообщает о смене минимального шага цены (Polymarket сужает шаг ближе к границам 0/100 для более точного прайсинга). Слушайте это событие и подстраивайте `minMove`/`precision` через `line.applyOptions(...)`, иначе будете тихо огрублять реальные движения цены около экстремумов.

### 5.3 Живые апдейты и бакетизация по ТФ

Ключевая механика: `series.update()` — если время бара совпадает с последним, он **перезаписывает** последнюю точку; если время больше — **добавляет** новую. На этом строится весь realtime + мульти-ТФ:

```js
let tfSeconds = 1;      // переключается кнопками 1с/5с/15с/30с/1м
let lastBucket = 0;

function pushTick(unixSec, priceUp01) {
  const bucket = Math.floor(unixSec / tfSeconds) * tfSeconds;
  if (bucket < lastBucket) return; // защита: не даём "уехать" во времени назад
  line.update({ time: bucket, value: priceUp01 * 100 });
  lastBucket = bucket;
}
```

Важно: `update()` требует, чтобы время не убывало — если вы попытаетесь передать метку раньше последней, будет ошибка. Данные с WebSocket теоретически могут прийти с небольшим дребезгом по времени (переподключение, две сети и т.п.) — без такой защиты приложение упадёт в проде на ровном месте.

**Никогда не вызывайте `setData()` на каждый тик** — это полная перерисовка всего датасета, она убьёт производительность на частых апдейтах. `setData()` — только для начальной загрузки истории и для полной перестройки при смене ТФ; всё живое — только через `update()`.

### 5.4 Переключение ТФ

Держите "базовый" буфер с разрешением 1 секунда (этого достаточно, отдельный буфер сырых тиков не нужен). При смене кнопки ТФ — один раз пересчитываете весь буфер в бакеты нужного размера (последнее значение в каждом бакете) и вызываете `setData()` один раз, дальше продолжаете `update()` в новом ритме.

### 5.5 Разрывы соединения

Если на пару секунд пропало соединение (переподключение, зомби-баг — см. раздел 6), не тяните линию через дыру произвольно — библиотека поддерживает "whitespace"-точки (объект `{ time }` без `value`), которые оставляют видимый разрыв вместо ложной прямой линии. После реконнекта сначала дёрните `/midpoint` или `/book` за снепшотом текущей цены, чтобы линия не "зависла" в ожидании следующего тика.

### 5.6 Производительность ("без тормозов")

Сама библиотека для этого и создана — она рисует на canvas и рассчитана на частые realtime-апдейты, так что дело почти всегда в том, как её использует приложение:

- если Polymarket шлёт события чаще, чем раз в кадр (при активной торговле — вполне реально), не вызывайте `update()` синхронно на каждое сообщение — копите последнее значение и сбрасывайте через `requestAnimationFrame` максимум раз за кадр;
- не пересоздавайте `chart`/`series` на каждый ре-рендер, если используете React — инициализируйте один раз в эффекте и дальше мутируйте императивно;
- буфер тиков в памяти браузера растёт неограниченно при долгой работе вкладки (86400 точек/сутки на 1с-разрешении) — это ещё не проблема для самой библиотеки, но если планируете держать вкладку открытой сутками, периодически прореживайте старые данные (например, старше 24–48 часов — сжимайте до 1-минутного разрешения) или переносите в IndexedDB.
- лицензия lightweight-charts (Apache-2.0) требует упоминания TradingView как создателя продукта в интерфейсе — это явное требование лицензии, отдельно прописанное в документации; не забудьте атрибуцию (обычно достаточно небольшой подписи/ссылки).

## 6. Прямое подключение vs relay — детали

Раз вы прямо спросили "как получать данные напрямую" — коротко резюмирую: технически ничего не мешает открыть `new WebSocket('wss://ws-subscriptions-clob.polymarket.com/ws/market')` прямо из браузерного JS и подписаться теми же фреймами, что и в примерах выше — CORS тут не действует так, как для HTTP-запросов, и явных признаков блокировки по Origin в документации нет. Это самый быстрый путь для одиночного/личного инструмента.

Единственное, что стоит проверить руками на старте (а не считать гарантированным): не режет ли Cloudflare-защита на этом конкретном эндпоинте запросы без "браузерного" контекста при деплое на статическом хостинге — просто откройте DevTools и посмотрите, приходят ли сообщения. Если что-то пойдёт не так — тонкий relay-сервер снимает вопрос полностью, поскольку у сервер-сервер соединений вообще нет понятия CORS/Origin-ограничений браузера.

## 7. Пошаговый план реализации

1. **Прототип данных без графика**: голый WS-клиент в консоли — подписаться на токены текущего 5-минутного рынка, залогировать 2-3 минуты сырых событий, убедиться, что понимаете формат book/price_change/last_trade_price и видите реальную частоту апдейтов.
2. **Резолвер рынка**: функция slug→tokenIds через Gamma, с парсингом JSON-строк и защитой от 404.
3. **Rollover-планировщик**: таймер на границы окна, pre-fetch следующего рынка, subscribe/unsubscribe на живом соединении, без пересоздания WS.
4. **Слой нормализации цены**: правило midpoint/last-trade (>$0.10 спред), бакетизация по 1 секунде, буфер в памяти.
5. **График**: инициализация lightweight-charts, привязка `pushTick`, ось 0-100, timeVisible/secondsVisible.
6. **Переключатель ТФ**: кнопки 1с/5с/15с/30с/1м → ресемплинг буфера → `setData()` один раз при переключении.
7. **Устойчивость**: reconnect с backoff, watchdog на "тишину" в сокете (см. ниже — это не гипотетический риск), whitespace на разрывах, снепшот через REST сразу после (пере)подписки.
8. **(опционально) Relay-сервер**, если нужен мультипользовательский режим или устойчивость к фоновым вкладкам.
9. **(опционально) Оверлей реальной цены BTC** — TWAP-поток из раздела 3, если захотите показывать "Price to Beat" рядом с вероятностной ценой.

## 8. ⚠️ Чек-лист ошибок и подводных камней

**Специфичное для Polymarket:**

- **TWAP-резолюция с 7 августа 2026** (раздел 3) — если когда-либо будете сверять "к чему идёт" рынок с реальной ценой BTC, используйте TWAP-поток, а не спот — иначе будете сравнивать несопоставимые числа.
- **"Зомби"-соединение WS.** Известная и подтверждённая проблема: CLOB WebSocket иногда принимает новые подключения и подписки, отвечает пустым массивом, но затем не присылает вообще никаких book/price_change событий — соединение остаётся открытым, PING/PONG работает нормально, а данные не идут часами. Из этого прямое следствие: **нельзя** считать "сокет открыт" синонимом "данные идут". Обязательно нужен watchdog — если для активного рынка нет ни одного сообщения дольше, скажем, 10-15 секунд, принудительно закрывайте и переоткрывайте соединение.
- `clobTokenIds`/`outcomes`/`outcomePrices` в ответах Gamma — JSON-строки, а не массивы, забыть `JSON.parse` — самая частая ошибка новичков с этим API.
- Перепутать Up/Down token id — график молча получится зеркальным.
- Tick size не фиксирован (может быть мельче 1 цента, особенно у границ 0/100) и меняется по ходу торгов через `tick_size_change` — не хардкодьте точность оси.
- `/prices-history` — минутная гранулярность и известный баг с пустым ответом на мелкой гранулярности для уже закрытых рынков — не годится как источник секундной истории.
- Два разных WS-хоста с разным интервалом heartbeat (10с у CLOB, 5с у RTDS) — не перепутайте таймеры при использовании обоих каналов.
- Rate limit'ы на практике не станут проблемой при правильном использовании (WS для потока, REST только для дискавери рынка) — но это перестаёт быть верным, если по ошибке начнёте поллить REST в цикле вместо WS.
- Гео-ограничения: Polymarket применяет блокировки по юрисдикциям для части функциональности — стоит явно проверить доступность нужных доменов именно с той сети/хостинга, где будет жить приложение, а не полагаться на то, что раз сайт открывается в браузере, то и API ответит оттуда же.
- Существует отдельный регулируемый продукт Polymarket US (`api.polymarket.us`, другая авторизация) — не имеет отношения к вашим ссылкам на `polymarket.com`, но если где-то в интернете встретите примеры под этот домен — это другой стек, не путайте.

**Специфичное для lightweight-charts:**

- v5 сломала API v4 (`addSeries(Type, opts)` вместо `addXSeries(opts)`) — много неактуальных примеров в сети.
- `timeVisible`/`secondsVisible` нужно выставлять явно, иначе секунды (а порой и время вообще) не отобразятся на оси.
- Время — это целые секунды unix (UTCTimestamp), не миллисекунды и не ISO-строка; `update()` требует неубывающего времени.
- Не гонять `setData()` на каждый тик — только `update()`.
- Лицензия требует атрибуции TradingView в интерфейсе.

**Общее, архитектурное:**

- Throttling апдейтов рендера через requestAnimationFrame при частом потоке.
- Ограничивать рост буфера в памяти при многодневной работе вкладки.
- Фоновые вкладки на мобильных браузерах троттлят таймеры — критично для точности 5-минутного rollover, если он завязан на клиентский `setTimeout`; при жёстких требованиях к точности выносите rollover-таймер на сервер.
- Использовать whitespace-точки для честного отображения разрывов вместо "склеивания" линии через дыры в данных.
