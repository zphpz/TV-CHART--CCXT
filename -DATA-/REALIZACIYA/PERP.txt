Да, это приложение лучше строить как **быстрый real-time терминал для rolling-маркетов Polymarket**: backend получает события через WebSocket, определяет текущий 5- или 15-минутный рынок, сохраняет поток цен с точностью до миллисекунд/секунды, а frontend отображает единую непрерывную историю через Lightweight Charts.

Главная техническая особенность: каждый rolling-маркет Polymarket — это не один постоянный инструмент, а последовательность отдельных рынков с разными `market ID`, `condition ID` и `token ID`. Поэтому нельзя просто постоянно слушать один URL или один токен.

## 1. Как устроены рынки

В Polymarket нужно разделять:

| Объект | Назначение |
|---|---|
| Event | Группа связанных рынков, отображаемая в URL |
| Market | Конкретный вопрос на определённый временной интервал |
| Token ID | Торгуемый токен конкретного исхода, например Up или Down |
| Condition ID | Идентификатор условия рынка |
| CLOB | Биржевой order book и сделки |

У бинарного BTC-рынка обычно есть два токена:

- `Up`;
- `Down`.

Цена токена представлена в диапазоне от `0.00` до `1.00`, поэтому для отображения в центах нужно использовать:

```text
chartPrice = polymarketPrice * 100
```

Например:

```text
0.50 → 50¢
0.73 → 73¢
0.18 → 18¢
```

У каждого рынка свои `token ID`, поэтому после окончания одного интервала приложение должно получить данные уже для следующего рынка. Polymarket официально описывает `event` как контейнер для одного или нескольких рынков, а `token IDs` — как идентификаторы ERC-1155-токенов, торгуемых через CLOB. [docs.polymarket](https://docs.polymarket.com/concepts/markets-events)

В приведённых ссылках есть важная ошибка:

```text
https://polymarket.com/event/btc-updown-15m
```

и

```text
https://polymarket.com/event/btc-updown-5m-1786491900
```

не обязательно указывают на актуальный 15-минутный и 5-минутный рынок. Один из URL указывает на конкретный уже завершённый временной интервал. Приложению нельзя строить логику только на фиксированном URL. Нужно регулярно находить актуальный рынок через Gamma API и проверять его поля `active`, `closed`, `endDate`, `startDate` и список `clobTokenIds`.

## 2. Рекомендуемая архитектура

Я бы использовал следующую структуру:

```text
Polymarket Gamma API
        │
        │ поиск текущего рынка
        ▼
Backend Market Resolver
        │
        │ token IDs текущего рынка
        ▼
Polymarket CLOB WebSocket
        │
        │ book / price_change / last_trade_price
        ▼
Normalizer + Aggregator
        │
        ├── запись в SQLite/PostgreSQL/ClickHouse
        ├── агрегация 1s/5s/15s/30s/1m
        └── WebSocket приложения
                    │
                    ▼
              Frontend
          Lightweight Charts
```

### Backend

Рекомендованный стек:

- Node.js;
- TypeScript;
- `ws` или официальный Polymarket client;
- Fastify или Hono для HTTP API;
- WebSocket для отправки данных браузеру;
- SQLite для локальной версии;
- PostgreSQL или TimescaleDB для длительной истории;
- Redis необязателен, если одновременно подключено много клиентов.

### Frontend

Рекомендованный стек:

- React или обычный TypeScript;
- Vite;
- Lightweight Charts 5.x;
- один `LineSeries`;
- WebSocket-клиент;
- Web Worker — желательно, если агрегация выполняется на браузере.

Lightweight Charts работает на HTML5 Canvas и предназначен именно для производительного отображения финансовых графиков. В актуальной документации указана версия 5.2; для real-time обновлений нужно использовать `series.update()`, а не постоянно вызывать `setData()`, поскольку `setData()` заменяет весь массив данных и может ухудшить производительность. [tradingview.github](https://tradingview.github.io/lightweight-charts/docs)

## 3. Поиск текущего рынка

### Вариант A — Gamma API

Сначала backend должен найти event или market по slug.

Общий подход:

```text
GET https://gamma-api.polymarket.com/events?slug=...
```

Затем из ответа нужно извлечь:

```json
{
  "id": "...",
  "slug": "...",
  "title": "BTC Up or Down 5m",
  "active": true,
  "closed": false,
  "markets": [
    {
      "id": "...",
      "conditionId": "...",
      "clobTokenIds": "[\"YES_TOKEN\", \"NO_TOKEN\"]",
      "outcomes": "[\"Up\", \"Down\"]",
      "active": true,
      "closed": false,
      "enableOrderBook": true,
      "startDate": "...",
      "endDate": "..."
    }
  ]
}
```

На практике поля могут отличаться по типам:

- `clobTokenIds` может приходить строкой с JSON-массивом;
- `outcomes` также может быть JSON-строкой;
- некоторые поля могут быть `null`;
- порядок токенов нельзя определять вслепую.

Обязательно нужно сопоставлять:

```text
outcomes[i] ↔ clobTokenIds[i]
```

То есть если API вернул:

```json
{
  "outcomes": "[\"Up\", \"Down\"]",
  "clobTokenIds": "[\"123\", \"456\"]"
}
```

то:

```text
Up   → 123
Down → 456
```

Нельзя предполагать, что первый токен всегда `Up`, хотя часто это так.

### Вариант B — поиск через список рынков

Если slug меняется или event endpoint возвращает неполную информацию, backend может искать рынки по нескольким признакам:

```text
title contains "Bitcoin"
title contains "Up or Down"
duration = 5m или 15m
active = true
closed = false
endDate > current_time
```

Не следует искать только по точному названию. Polymarket может менять формат:

```text
BTC Up or Down
Bitcoin Up or Down
Bitcoin Up or Down - 5m
BTC Up or Down - August 13, 12:00AM-12:05AM
```

Лучше хранить собственную конфигурацию:

```ts
type MarketConfig = {
  durationSeconds: 300 | 900;
  slugPrefixes: string[];
  outcomeName: string;
};
```

Например:

```ts
const configs = {
  btc5m: {
    durationSeconds: 300,
    slugPrefixes: ['btc-updown-5m', 'bitcoin-up-or-down-5m'],
    outcomeName: 'Up',
  },
  btc15m: {
    durationSeconds: 900,
    slugPrefixes: ['btc-updown-15m', 'bitcoin-up-or-down-15m'],
    outcomeName: 'Up',
  },
};
```

### Определение смены рынка

Не стоит ждать только WebSocket-события `market_resolved`. Надёжнее использовать несколько механизмов:

1. Проверять время окончания текущего рынка.
2. Каждые 2–5 секунд запрашивать информацию о следующем рынке.
3. Обрабатывать WebSocket-события `new_market` и `market_resolved`.
4. Проверять, что старый рынок действительно стал `closed` или `resolved`.
5. После смены рынка получать новые `token ID`.
6. Подписываться на новый токен до окончания старого интервала.

Идеальный переход:

```text
T - 10 секунд:
    найти следующий рынок

T - 3 секунды:
    получить его metadata и token IDs

T:
    подписаться на новый token ID

T + 1–2 секунды:
    переключить activeMarket

T + несколько секунд:
    удалить старый токен из подписки
```

Лучше некоторое время слушать старый и новый токен одновременно, чтобы не потерять события на границе.

CLOB WebSocket позволяет добавлять и удалять `asset IDs` без открытия нового соединения через операции `subscribe` и `unsubscribe`. [docs.polymarket](https://docs.polymarket.com/market-data/realtime-data)

## 4. Получение real-time данных

Основной WebSocket Polymarket:

```text
wss://ws-subscriptions-clob.polymarket.com/ws/market
```

Подписка:

```json
{
  "assets_ids": [
    "<UP_TOKEN_ID>",
    "<DOWN_TOKEN_ID>"
  ],
  "type": "market"
}
```

Polymarket указывает, что market stream может присылать:

- `book`;
- `price_change`;
- `last_trade_price`;
- `tick_size_change`;
- `best_bid_ask`;
- `new_market`;
- `market_resolved`.

Для графика цены полезнее всего использовать:

1. `last_trade_price`;
2. `best_bid_ask`;
3. `book`.

Документация Polymarket описывает эти события и их поля, включая `price`, `bestBid`, `bestAsk`, `timestamp`, `side` и `transactionHash`. [docs.polymarket](https://docs.polymarket.com/market-data/realtime-data)

### Какую цену показывать

Это принципиально важно. «Цена рынка» может означать несколько разных значений.

#### Вариант 1 — последняя сделка

```text
price = last_trade_price
```

Преимущества:

- отражает реально совершённую сделку;
- хорошо подходит для исторического графика;
- легко хранить;
- меньше ложных скачков, вызванных пустым order book.

Недостаток:

- если сделок долго нет, цена остаётся старой.

#### Вариант 2 — midpoint

```text
mid = (bestBid + bestAsk) / 2
```

Преимущества:

- обновляется при изменении order book;
- лучше отражает текущую оценку рынка;
- удобен для плавной линии.

Недостатки:

- midpoint может существовать даже без сделки;
- при широком spread он может быть неисполняемой условной ценой;
- после исчезновения ликвидности может стать бессмысленным.

#### Вариант 3 — цена покупки

Если пользователь хочет увидеть, сколько стоит купить `Up`, нужно использовать лучший ask:

```text
buyPrice = bestAsk
```

Polymarket отдельно отмечает, что для запроса `BUY` возвращается минимальный ask, то есть цена, по которой можно купить токен; для `SELL` — максимальный bid. [docs.polymarket](https://docs.polymarket.com/market-data/prices-order-books)

### Рекомендация

Сделать переключатель источника:

```text
Last trade
Midpoint
Best bid
Best ask
```

По умолчанию я бы выбрал:

```text
основная линия = midpoint
точки сделок = last trade
```

Либо для наиболее консервативной истории:

```text
основная линия = last trade
```

И в интерфейсе показывать:

```text
Last: 54.00¢
Bid: 53.00¢
Ask: 55.00¢
Mid: 54.00¢
Spread: 2.00¢
```

### Heartbeat и переподключение

CLOB WebSocket требует application-level heartbeat. В текущей документации указано, что нужно отправлять текстовый кадр:

```text
PING
```

каждые 10 секунд, после чего сервер отвечает:

```text
PONG
```



Backend должен иметь:

```ts
setInterval(() => {
  if (socket.readyState === WebSocket.OPEN) {
    socket.send('PING');
  }
}, 10_000);
```

Также обязательны:

- автоматическое переподключение;
- повторная подписка;
- exponential backoff;
- защита от нескольких параллельных reconnect;
- проверка времени последнего события;
- повторный REST snapshot после восстановления.

Пример задержек:

```text
1 секунда
2 секунды
5 секунд
10 секунд
30 секунд
60 секунд
```

После reconnect нельзя считать, что локальное состояние актуально. Нужно:

1. получить новый order book;
2. получить last trade;
3. заново подписаться;
4. пометить промежуток как возможный gap;
5. при необходимости загрузить REST-историю.

## 5. История и секундные данные

### Важное ограничение Polymarket

REST endpoint `/prices-history` подходит для исторической загрузки, но его стандартная агрегация связана с минутами. Он принимает:

```text
market
startTs
endTs
interval
fidelity
```

`interval` позволяет выбирать окна вроде `1h`, `6h`, `1d`, `1w`, `max`, а `fidelity` задаёт интервал агрегации в минутах. [docs.polymarket](https://docs.polymarket.com/api-reference/markets/get-prices-history)

Это означает:

- REST-история может быть полезна для начальной загрузки;
- она не гарантирует полноценную секунду за секундой;
- нельзя рассчитывать, что Polymarket отдаст вам месячную историю с точностью 1 секунда;
- для настоящей секундной истории нужно самостоятельно записывать WebSocket-события.

Дополнительно документация указывает, что при подписке market stream может сначала передать предшествующие две минуты данных, после чего продолжить live-поток. Это удобно для инициализации, но недостаточно для полной исторической базы. [docs.polymarket](https://docs.polymarket.com/market-data/realtime-data)

### Собственный recorder

Каждое событие нужно сохранять примерно в таком формате:

```sql
CREATE TABLE price_ticks (
    id INTEGER PRIMARY KEY,
    market_id TEXT NOT NULL,
    condition_id TEXT,
    token_id TEXT NOT NULL,
    outcome TEXT NOT NULL,
    event_time_ms INTEGER NOT NULL,
    received_time_ms INTEGER NOT NULL,
    source TEXT NOT NULL,
    price REAL,
    best_bid REAL,
    best_ask REAL,
    midpoint REAL,
    size REAL,
    side TEXT,
    transaction_hash TEXT,
    is_gap INTEGER DEFAULT 0
);
```

Нужно хранить два времени:

```text
event_time_ms    — время события Polymarket
received_time_ms — время получения вашим backend
```

Это позволяет видеть задержку:

```text
latency = received_time_ms - event_time_ms
```

Если WebSocket присылает timestamp в миллисекундах:

```ts
const eventTime = Number(message.timestamp);
```

Если timestamp оказался в секундах:

```ts
const eventTimeMs =
  eventTime < 10_000_000_000
    ? eventTime * 1000
    : eventTime;
```

Но лучше определять формат явно по документации конкретного события и не полагаться только на эвристику.

### Как создавать точку каждую секунду

Входящие события не обязательно приходят ровно раз в секунду. Может быть:

```text
0 событий за секунду
1 событие
20 событий
несколько событий с одинаковым timestamp
```

Поэтому нужно создать собственный секундный агрегатор.

Для каждой секунды:

```text
bucket = floor(eventTimeMs / 1000) * 1000
```

Если в одну секунду пришло несколько событий, можно сохранить:

```text
open  — первая цена
high  — максимум
low   — минимум
close — последняя цена
```

Хотя пользователь хочет линию, я бы всё равно хранил OHLC-агрегацию:

```sql
CREATE TABLE price_bars (
    market_id TEXT NOT NULL,
    token_id TEXT NOT NULL,
    timeframe TEXT NOT NULL,
    bucket_time_ms INTEGER NOT NULL,
    open REAL,
    high REAL,
    low REAL,
    close REAL,
    last_trade REAL,
    best_bid REAL,
    best_ask REAL,
    midpoint REAL,
    tick_count INTEGER,
    PRIMARY KEY (market_id, token_id, timeframe, bucket_time_ms)
);
```

Для line chart можно показывать:

```text
close
```

А при необходимости позже добавить свечи.

### Что делать, если в секунде нет события

Не следует автоматически считать это ошибкой. Возможны два режима.

#### Режим 1 — ступенчатая линия

Последняя известная цена продолжается до следующего события:

```text
10:00:01 → 50.0
10:00:02 → 50.0
10:00:03 → 50.0
10:00:04 → 51.0
```

Это хорошо показывает, что цена не менялась в потоке наблюдений.

#### Режим 2 — пропуск

Если событий нет, точку не создавать. Тогда линия будет соединять две известные цены.

Для торгового терминала лучше использовать ступенчатый режим, но визуально помечать отсутствие новых событий. Например:

```text
lastUpdateAge: 4.8s
status: STALE
```

Если данных нет больше 5–10 секунд, линия не должна создавать иллюзию свежей цены.

## 6. Объединение последовательных рынков

Есть два возможных режима отображения.

### Режим A — отдельная история каждого рынка

Каждый market отображается отдельно:

```text
Market #1: 12:00–12:05
Market #2: 12:05–12:10
Market #3: 12:10–12:15
```

Преимущество — точная историческая информация.

Недостаток — при переключении рынка линия может начинаться заново с 50¢.

### Режим B — непрерывный rolling-график

Для пользователя это, вероятно, более удобно:

```text
старый рынок → новый рынок → следующий рынок
```

При переходе:

1. старый рынок закрывается;
2. новая линия создаётся с первой реальной ценой;
3. между рынками отображается вертикальный разделитель;
4. на разделителе показывается новый интервал.

Важно: нельзя трактовать переход с `99¢` старого рынка на `50¢` нового как реальное падение с 99 до 50. Это две разные вероятностные шкалы разных контрактов.

Поэтому на графике нужно визуально показать:

```text
Market boundary
```

Например:

- вертикальная пунктирная линия;
- метка `12:05 — new market`;
- другой фон для каждого рынка;
- tooltip с `marketId`.

Также можно сделать два режима:

```text
Continuous rolling
Per-market
```

### Нормализация относительно старта

Поскольку каждый новый контракт начинается около 50¢, можно отображать:

```text
deltaFromStart = currentPrice - firstPrice
```

Например:

```text
50¢ → 0¢
57¢ → +7¢
43¢ → −7¢
```

Но основная шкала всё равно должна оставаться от 0 до 100.

## 7. Таймфреймы 1s, 5s, 15s, 30s, 1m

Нужно разделить:

```text
raw ticks
```

и отображаемые бары.

Хранилище принимает всё:

```text
каждое last_trade_price
каждое изменение bid/ask
каждое изменение midpoint
```

Затем агрегатор формирует бары:

```text
1s  → 1-секундные бары
5s  → 5-секундные бары
15s → 15-секундные бары
30s → 30-секундные бары
1m  → минутные бары
```

Для каждого бара:

```ts
type Bar = {
  time: number;
  open: number;
  high: number;
  low: number;
  close: number;
  tickCount: number;
};
```

Алгоритм:

```ts
function updateBar(
  bar: Bar | undefined,
  timeMs: number,
  price: number,
  intervalMs: number,
): Bar {
  const bucket = Math.floor(timeMs / intervalMs) * intervalMs;

  if (!bar || bar.time !== bucket) {
    return {
      time: bucket,
      open: price,
      high: price,
      low: price,
      close: price,
      tickCount: 1,
    };
  }

  return {
    ...bar,
    high: Math.max(bar.high, price),
    low: Math.min(bar.low, price),
    close: price,
    tickCount: bar.tickCount + 1,
  };
}
```

Для line series в Lightweight Charts:

```ts
const lineSeries = chart.addSeries(LineSeries, {
  color: '#2962FF',
  lineWidth: 2,
  priceFormat: {
    type: 'custom',
    formatter: (value: number) => `${value.toFixed(1)}¢`,
  },
  autoscaleInfoProvider: () => ({
    priceRange: {
      minValue: 0,
      maxValue: 100,
    },
  }),
});
```

Затем:

```ts
lineSeries.update({
  time: Math.floor(bar.time / 1000),
  value: bar.close,
});
```

Если нужен фиксированный диапазон 0–100, настройку масштаба нужно проверить на конкретной версии Lightweight Charts. В некоторых версиях нужно использовать `autoscaleInfoProvider`, а в других — горизонтальные price lines на 0 и 100. Не стоит рассчитывать, что обычный autoscale сам будет всегда держать шкалу от 0 до 100.

## 10. Обязательно учитывать источник разрешения

Цена токена Polymarket — это мнение участников рынка, а не сам BTC/USD. При этом конкретный BTC Up/Down market может разрешаться по Chainlink BTC/USD TWAP.

На странице одного из таких рынков Polymarket указано, что результат определяется через Chainlink BTC/USD TWAP, а не через произвольную цену Binance, Bybit или другого spot-рынка. [polymarket](https://polymarket.com/event/btc-updown-5m-1786491900)

Это значит, что приложение желательно разделить на два независимых потока:

```text
1. Цена контракта Polymarket: Up/Down в центах
2. Reference price: BTC/USD Chainlink или другой источник
```

Для точного анализа можно отображать их одновременно:

- верхний график: `Up price`, 0–100¢;
- нижний график: `BTC/USD reference`;
- вертикальная линия начала рынка;
- горизонтальная или текстовая отметка `Price to Beat`.

Polymarket RTDS также предоставляет Chainlink TWAP-потоки для BTC/USD с окнами 30 и 60 секунд. Для RTDS используется WebSocket:

```text
wss://ws-live-data.polymarket.com
```

а для TWAP предусмотрены отдельные темы для 30- и 60-секундного окна. [docs.polymarket](https://docs.polymarket.com/market-data/chainlink-twap)

Но важно: Chainlink TWAP 30 секунд — это lookback-окно, а не обязательная частота публикации. Нельзя считать, что каждое обновление приходит строго раз в 30 секунд.

## 11. Возможные ошибки

### Ошибки идентификации рынка

- фиксированный slug указывает на старый рынок;
- ссылка на 15m фактически содержит 5m;
- текущий рынок уже закрыт;
- следующий рынок ещё не появился;
- событие содержит несколько рынков;
- `clobTokenIds` пришёл JSON-строкой;
- порядок `outcomes` неверно интерпретирован.

Решение:

- проверять metadata;
- не доверять одному slug;
- валидировать `active`, `closed`, `enableOrderBook`, `startDate`, `endDate`;
- хранить immutable mapping `marketId → tokenId → outcome`.

### Ошибки времени

- секунды перепутаны с миллисекундами;
- используется локальное время вместо UTC;
- часы backend отстают;
- время события и время получения не различаются;
- окно рынка рассчитано по локальному часовому поясу.

Все внутренние timestamp нужно хранить в UTC Unix milliseconds. В интерфейсе можно отображать EEST или локальный часовой пояс пользователя.

### Потеря WebSocket-событий

Причины:

- разрыв интернета;
- серверное закрытие соединения;
- отсутствие heartbeat;
- медленная обработка сообщений;
- неправильная повторная подписка;
- смена рынка во время reconnect.

Решение:

- watchdog;
- ping/pong;
- reconnect;
- повторный snapshot;
- журнал gaps;
- маркировка данных после разрыва;
- не рисовать «непрерывную» историю, если в ней есть пропуск.

### Ошибки выбора цены

- last trade слишком долго не обновляется;
- midpoint показывает цену при пустой ликвидности;
- best ask отсутствует;
- bid выше ask из-за неконсистентного состояния;
- цена временно равна 0 или 1;
- некоторые сделки могут быть аномальными.

Нужно фильтровать только технически некорректные значения:

```text
price < 0 → reject
price > 1 → reject
NaN → reject
bid > ask → mark invalid
```

Но не следует бездумно удалять цену 0 или 1: у завершённых либо почти разрешённых рынков такие значения могут быть реальными.

### Ошибки истории

- REST history имеет минутную гранулярность;
- старый рынок больше недоступен в нужной детализации;
- данные на границе рынков дублируются;
- один тик приходит несколько раз;
- сообщения приходят не по порядку;
- позднее событие имеет более ранний timestamp.

Нужны:

- сортировка по `event_time_ms`;
- дедупликация по `transactionHash`, если он присутствует;
- fallback key из `tokenId + timestamp + price + size`;
- отдельное хранение raw events;
- возможность пересобрать бары заново.

## 12. Оптимизация производительности

Чтобы приложение не тормозило:

- не вызывать `setData()` при каждом тике;
- использовать `series.update()`;
- держать raw recorder на backend;
- на frontend передавать уже агрегированные данные;
- ограничивать число точек в видимом окне;
- не перерисовывать React-компонент на каждый тик;
- хранить текущий bar в обычной переменной или Zustand store;
- использовать Web Worker для тяжёлой агрегации;
- включить backpressure;
- отправлять клиентам не каждый raw event, а максимум 5–20 обновлений в секунду;
- историю подгружать порциями;
- не открывать новый WebSocket на каждый rolling-рынок.

Например, backend может получать 100 событий в секунду, но frontend получать:

```text
1 обновление каждые 100–200 мс
```

При этом все raw-события всё равно сохраняются на сервере.

Для одного графика с несколькими часами истории не нужно отправлять все тики. При выбранном `1m` достаточно минутных баров. При выбранном `1s` можно отправлять только секунды, попавшие в видимый диапазон.

## Итоговая рекомендация

Оптимальная реализация выглядит так:

```text
Backend:
  TypeScript + Node.js
  Gamma API для поиска rolling-рынков
  CLOB WebSocket для цен и order book
  SQLite/PostgreSQL для собственной истории
  WebSocket сервера для frontend

Frontend:
  React + Vite
  Lightweight Charts 5.x
  LineSeries
  фиксированная шкала 0–100
  таймфреймы 1s/5s/15s/30s/1m

Главная цена:
  midpoint или last trade

История:
  записывать самостоятельно из WebSocket

Смена рынка:
  по времени + REST metadata + WebSocket events

Надёжность:
  heartbeat, reconnect, resubscribe, snapshot, gap detection
```

Самая важная идея: **не пытаться получать секундную историческую информацию задним числом из Polymarket REST API**. REST можно использовать для начальной загрузки, но полноценную историю 1s нужно собирать самостоятельно, начиная с момента запуска recorder. Иначе через несколько часов или дней у вас будет только частично агрегированная история, а не точный поток движения цены.
